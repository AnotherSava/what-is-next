# Project guidelines — What's Next

## Local development

- **The local dev server runs strictly on port 3939 — never Next.js's default 3000.** The port lives in `config/deploy.env` (`DEV_PORT=3939`, `DEV_DIR=web`).
- **Launch/restart it with `deploy` (or `bash scripts/deploy.sh`) — either works from any directory.** Both resolve the repo root and read `config/deploy.env`, so the server always comes up on 3939: the `deploy` shell function walks up to the repo root via `run_repo_script`, and the underlying deploy scripts independently resolve the root (nearest ancestor holding `config/deploy.env`, via the shared `_repo-dir.sh` helper). `deploy` is just shorter.
- **Never run a second dev server *for this project* on another port.** Next.js 16 allows only one dev server per project directory: starting a second `next dev` for `web/` (even on a different port) makes the new one defer to the already-running instance, so 3939 never actually comes up even though `deploy` reports "ready" and the port briefly opens. Symptom: `http://localhost:3939` unreachable while a stray what-is-next `next dev` (one started by hand on another port) is alive. Fix: stop the stray instance, then restart 3939. (Dev servers of *other* projects — e.g. printlab on 3000 — don't conflict; the lock is per-project, not machine-wide.) Access the app only at `http://localhost:3939`.
- **Restart the dev server after `prisma generate`.** A running `next dev` keeps a stale in-memory Prisma client, so pages touching a newly added model/field throw `Cannot read properties of undefined` / "unknown field" 500s until restart.
- **Run `npx prisma generate` explicitly after `prisma migrate dev`.** Its built-in generate step didn't refresh the generated client here — `tsc` kept reporting a just-added field as nonexistent until an explicit `prisma generate` (then restart dev, per the note above).
- **`prisma migrate dev` aborts in this non-interactive shell** ("environment is non-interactive, which is not supported" — even with `--name` or `--create-only`). To add a migration, hand-author `prisma/migrations/<YYYYMMDDHHMMSS>_<name>/migration.sql` (for a nullable column + index that's just `ALTER TABLE … ADD COLUMN` + `CREATE … INDEX` — no table rebuild) then apply with `doppler run -- npx prisma migrate deploy`, then `npx prisma generate` and restart dev (per the notes above).
- **`prisma db execute` reads `prisma.config.ts`, not `--schema` (Prisma 7).** Passing `--schema` fails with "unknown or unexpected option: --schema" — drop it. To run one-off raw SQL against the dev DB (e.g. flip a `Setting` flag to A/B a behavior), use `doppler run -- npx prisma db execute --stdin <<'SQL' … SQL`. It executes statements only and prints no query results, so read rows back with a small `PrismaClient` script or Prisma Studio.
- **Deleting an app route can leave a stale `.next/types` type error.** After removing a `page.tsx` route, `npx tsc --noEmit` may fail with `Cannot find module '.../page.js'` from `.next/types/validator.ts` — a leftover from a prior `next build` that dev never regenerates (dev uses `.next/dev/types/`); a dev-server restart doesn't clear it. Fix: `rm -rf .next/types` (regenerates on the next build).
- **The claude-in-chrome browser-extension screenshot tools can't capture the running dev server.** Turbopack `next dev` pages never reach the extension's `document_idle`, so content-script injection times out (`Script injection timed out after 5000ms`; `read_page` waits ~45s). It hits every route (reproduced on `/shows`, not just newly-added pages) — a dev-server/extension interaction, not a page bug. To confirm a UI change, rely on `tsc` + `vitest` + a server-side `200`, or open `http://localhost:3939` yourself; don't burn turns retrying screenshots. **`javascript_tool` is the exception — it uses a different injection path and works fine on these pages**, so DOM text and `getBoundingClientRect()` geometry are available for probing (e.g. measuring rendered text width in the real webfont before hard-coding a column width). Reach for it before trying to launch a headless Chrome — `chrome-devtools` MCP needs Chrome already on `--remote-debugging-port=9222`, and a hand-launched headless instance never wrote its `DevToolsActivePort` here.
- **Turbopack `next dev` serves stale CSS — for `globals.css` edits AND for new utility classes introduced in a component.** A newly-used arbitrary/variant class (`w-[74px]`, `@2xl:grid-cols-2`, `disabled:opacity-45`) can be absent from the served chunk until a clean rebuild, so a layout silently doesn't apply. Newly-*added* rule blocks compile, but *modified values on existing rules* often keep serving the previously-compiled value — a plain reload or `touch` doesn't reliably refresh them (the served `/_next/static/chunks/*.css` keeps the same name and byte-identical old content). A *structural* edit (changing a selector, adding/removing a property) forces a fuller recompile than a pure value tweak. Reliable fix when the served CSS lags the source: stop the server, `rm -rf web/.next`, restart. Verify what's actually served by fetching the page's linked `*.css` chunk and grepping for the rule — don't trust a browser reload alone.
- **Run one-off scripts with the app's real code via tsx.** `doppler run -- npx tsx --tsconfig tsconfig.json <script.mts>` from `web/` resolves the `@/` alias and loads app modules — e.g. `getPrisma` (with its better-sqlite3 adapter), `getTmdb`, `hydrateMovieByTmdbId` — so a data fix reuses the real hydration/logic instead of hand-writing fields (repoint a MediaItem's `tmdbId`, then re-run `hydrateMovieByTmdbId` to overwrite metadata + refetch the OMDb rating). The Prisma client is generated to `src/generated/prisma` (imported as `@/generated/prisma/client`), so a bare `@prisma/client` import fails; for quick *read-only* inspection, open `web/prisma/dev.db` directly with `better-sqlite3` (`new Database(file, { readonly: true })`).
- **Run `prettier --write` only on files you created or substantially rewrote — never on a file you edited lightly.** The tree is not prettier-clean (37 of the `src/**` files fail `prettier --check`), so `--write` on one of them reformats swathes of untouched code into the pending diff. It also fights the global "prefer single-line expressions" rule by wrapping long single-line JSX attributes and calls. To check whether a formatting run would stay inside your own edit, copy the file, `--write`, `diff -u` the copy against the result, and restore the copy — then apply for real only if every hunk is yours.
- **When stopping the dev server by process match, match the `next dev` / `next-server` command signature — never the port `3939`.** The port string can appear in unrelated processes' command lines (it turned up in a running Chromium-based browser's field-trial/handle args), so a `-match '3939'` kill can force-terminate the user's browser tabs. Multiple stray `next dev` instances on 3939 (doppler-wrapped, plain, `npm run dev`) can also coexist and fight for the port — clear them all by the `next dev` signature, then start one.
